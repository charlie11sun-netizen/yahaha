> 记录范围：本次集中修复的 6 个后端生产风险点。目标是把关键入口从“依赖外部服务时 fail-open”或“只靠 API 层约定”收紧为后端强约束。

## 1. 内容审核 fail-open

### 问题

LLM 内容审核异常时会生成 `action="error"`，但原来的同步入口只在 `decision.blocked` 时拦截。生成任务里的 `safety_intake` 也会吞掉审核异常并继续接受 prompt。

这意味着生产环境即使配置了 `MODERATION_MODE=enforce`，审核 provider 抖动时仍可能放行用户输入或外显文本。

### 解决方案

- 在 `ModerationDecision` 增加 `errored` 判断。
- `ensure_allowed()` 在 enforce 模式下同时拦截 `blocked` 和 `errored`：
  - `blocked` 返回 `422 MODERATION_BLOCKED`。
  - `errored` 返回 `503 MODERATION_UNAVAILABLE`。
- 生成链路的 safety intake 在 enforce 模式下遇到审核异常直接失败，不再继续进入生成流程。
- 保留 log 模式行为：非 enforce 下仍记录审核事件，便于灰度观察，不强制阻断。

## 2. Redis 限流 fail-open

### 问题

限流依赖 Redis。Redis 不可用时，原逻辑直接放行请求，导致登录、注册、任务创建、评论等入口在 Redis 故障期间失去保护。

### 解决方案

- 新增并默认关闭 `RATE_LIMIT_FAIL_OPEN`，即默认 `false`。
- Redis 限流异常时默认返回 `503 RATE_LIMIT_UNAVAILABLE`。
- 保留显式逃生开关：只有在环境变量中主动设置 `RATE_LIMIT_FAIL_OPEN=true` 时，才允许 Redis 故障期间放行。
- `.env.example` 和 `.env.prod.example` 同步声明该配置，避免生产环境默认误用 fail-open。

## 3. 推荐和列表分页

### 问题

`related_games()` 原来会拉取全量 published 游戏后在 Python 里打分。`/tasks`、用户游戏列表、当前用户游戏和收藏列表也缺少分页。

数据量上来后，这些接口会先出现响应变慢、内存占用上升和超时。

### 解决方案

- 新增分页工具，统一规范 `limit/offset`，限制最大 `limit`。
- `/tasks`、`/users/{id}/games`、`/me/games`、`/me/favorites` 支持分页，并返回 `total`、`limit`、`offset`、`has_more`。
- `related_games()` 改为数据库侧计算：
  - tag overlap 使用 SQL 聚合。
  - genre match 使用 SQL `case`。
  - 再按 score、播放数、发布时间和创建时间排序。
- 推荐接口只取有限结果，不再拉全量 published 游戏到 Python 内存中打分。

## 4. Prompt 长度限制前移

### 问题

`TaskCreateIn.idea` 原来只有 `min_length=1`。真正的 2000 字符限制在 worker 的 safety intake 中才执行。

结果是超大 prompt 会先通过 API 入库、提交事务、入队，之后才在 worker 阶段失败，浪费数据库、队列和 worker 资源。

### 解决方案

- 在请求 schema 层将 `TaskCreateIn.idea` 改为 `Field(min_length=1, max_length=2000)`。
- 超长 prompt 在 API 入参校验阶段直接返回 422，不再创建任务、不入库、不入队。
- worker 侧原有长度保护继续保留，作为纵深防御。

### 涉及文件

- [`backend/app/schemas.py`](../backend/app/schemas/__init__.py)
- [`backend/tests/test_tasks.py`](../backend/tests/api/test_tasks.py)

## 5. 任务并发额度竞态

### 问题

用户活跃任务额度检查是“count 再 insert”。并发请求可能同时完成 count，随后都 insert，突破 `MAX_ACTIVE_TASKS_PER_USER`。

同一游戏只允许一个活跃 revision 的检查也有同类竞态。

### 解决方案

- 将额度检查逻辑集中到 `backend/app/services/task_actions.py`。
- PostgreSQL 下在检查前获取事务级 advisory lock：
  - 用户活跃任务额度锁：`task_active_user:{user_id}`。
  - 单游戏活跃 revision 锁：`task_revision_game:{game_id}`。
- 锁在事务结束时自动释放，保证同一用户或同一游戏的并发创建请求串行化执行检查和插入。
- SQLite 和非 PostgreSQL 环境下该锁 helper no-op，保证本地测试和轻量环境兼容。

## 6. S3 游戏产物公开下载

### 问题

生产 compose 原来将 `games/` 前缀设置为匿名 download。API 层虽然保护 draft/preview 可见性，但如果对象 URL 泄露，访问方可以绕过 API，直接读取 preview 或 draft 产物。

### 解决方案

- 从生产 compose 中移除 `games/` 前缀匿名 download 配置。
- 新增运行时 URL 签名模块：
  - manifest 仍通过 API 读取。
  - manifest 内的 `entry_url` 和 `files[].url` 改写为 `/games/{game_id}/files/{token}/{version}/{path}`。
  - token 使用 `JWT_SECRET` 做 HMAC 签名，包含 `game_id`、`version`、过期时间，默认有效期 1 小时。
- 文件读取继续经过 API：
  - 先校验游戏可见性。
  - 再校验 token、version、path。
  - 校验通过后由后端读取对象并返回。
- 对该文件路径做精确例外：
  - 允许 iframe 加载游戏文件。
  - 仍要求 token，不恢复公开桶访问。

## 后续注意事项

- 生产环境应保持 `MODERATION_MODE=enforce`，并把审核 provider 的 503 纳入告警。
- 生产环境应保持 `RATE_LIMIT_FAIL_OPEN=false`，只有在明确接受风险的事故处置窗口中临时打开。
- S3/MinIO 不应再为 `games/` 前缀配置匿名读取；公开试玩通过 API 受控文件 URL 实现。
- advisory lock 方案依赖 PostgreSQL。若未来切换数据库，需要重新设计等价的并发约束。
