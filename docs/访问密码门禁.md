# 整站访问密码门禁（Site Access Gate）

> 配套：[README](../README.md) · [安全与可观测性](安全与可观测性.md) · [系统架构](系统架构.md)
> 目的：给**部署后**的实例加一道「前门口令」，防止 demo 被公网随意打开。
> 更新日期：2026-06-20

---

## 1. 这是什么 / 为什么

平台本身已有**用户**注册/登录（邮箱 JWT + OAuth）。但那是「谁在用」，不是「能不能打开这个站」。
当我们把实例部署到公网做演示时，希望先有一道**整站口令**：输对了才进得去。

- **一个开关**：环境变量 `SITE_PASSWORD`。留空（默认）= 不启用，本地开发与 `docker compose up` 行为不变；设了值 = 全站门禁开启。
- **两层防护**：前端页面门 + 后端 API 门，共用同一个密码，**与用户登录相互独立**。
- **密码只在服务端**：`SITE_PASSWORD` 不是 `NEXT_PUBLIC_*`，不会进浏览器打包产物；cookie / 请求头里携带的是密码的**哈希令牌**，不是明文。

---

## 2. 总览

| 层 | 位置 | 拦截方式 | 凭证 |
| --- | --- | --- | --- |
| **前端页面门** | `frontend/middleware.ts`（Next Edge 中间件） | 未解锁 → 重定向到 `/gate` 口令页 | httpOnly cookie `pf_gate` |
| **后端 API 门** | `backend/app/main.py` 的 `site_gate` 中间件 | 未带令牌 → `401` | 请求头 `X-Gate-Token` |

两层共用同一个令牌，算法在前后端**逐字节一致**：

```
token = sha256( "gameweave-gate:v1:" + SITE_PASSWORD.trim() )   # 小写 hex
```

- 前端：`frontend/lib/gate.ts` 用 Web Crypto（`crypto.subtle.digest`，Edge + Node 通用）
- 后端：`backend/app/core/gate.py` 用 `hashlib.sha256`

> **为什么后端用「请求头」而不是直接读 cookie？**
> 浏览器是**跨源直连**后端的（`NEXT_PUBLIC_API_BASE_URL`，如 `:3000` 前端调 `:8000` 后端），
> 前端那个 `pf_gate` cookie 不会自动带到后端去。所以前端解锁后把令牌放进一个**可读** cookie，
> 由 API 客户端读出、作为 `X-Gate-Token` 头随每次请求发给后端。

---

## 3. 启用方式

在根目录 `.env` 设置密码，然后重建前后端容器：

```bash
# .env
SITE_PASSWORD=你的密码

docker compose up -d --build web api
```

环境变量注入：

- `web`（前端）：`docker-compose.yml` 的 `web.environment` 里 `SITE_PASSWORD: ${SITE_PASSWORD:-}`
- `api`（后端）：复用已有的 `env_file: .env`，自动读到

> 留空或不设 = 门禁关闭。`docker compose up`（默认 `.env.example` 复制过来）即开放，无需任何额外操作。

## 4. 工作原理

### 4.1 解锁流程

```
浏览器 → GET /any            (无 pf_gate cookie)
  └─ Next middleware: 整站门禁开 & 无有效 cookie
        → 302 /gate?next=/any
浏览器 → /gate 口令页，输入密码，POST /api/gate { password }
  └─ 路由校验（常数时间比较 SITE_PASSWORD）
        ✓ 命中 → Set-Cookie:
             pf_gate        (httpOnly，驱动前端页面门，JS 不可读、不可伪造)
             pf_gate_token  (可读，值=令牌，供 API 客户端取用)
        ✗ 未命中 → 401，页面提示 "Incorrect password"
浏览器 → router.replace(next) 回到原页面，整站解锁
```

### 4.2 解锁后的每次后端请求

```
api.ts req() → gateHeader() 从 pf_gate_token cookie 取令牌
            → 附加请求头 X-Gate-Token: <token>
后端 site_gate 中间件 → 比对 expected_token()
   ✓ 一致 → 放行到路由
   ✗ 缺失/不符 → 401 { detail: "Site locked..." }
```

涉及文件：
- 前端取令牌并附头：`frontend/lib/api.ts`（`gateHeader()`）
- 下发双 cookie：`frontend/app/api/gate/route.ts`（`POST` 设置，`DELETE` 清除＝重新上锁）
- 旧会话兼容：`frontend/middleware.ts` 对「有 `pf_gate` 但缺 `pf_gate_token`」的会话**回填**可读令牌，无需重新解锁
- 口令页：`frontend/app/gate/page.tsx`（shadcn 风格，整屏居中；`frontend/components/Nav.tsx` 在 `/gate` 隐藏顶栏）

### 4.3 cookie 属性

| cookie | httpOnly | 作用 | 备注 |
| --- | --- | --- | --- |
| `pf_gate` | ✅ | 前端页面门校验 | JS 不可读，防伪造 |
| `pf_gate_token` | ❌ | 供 `api.ts` 读出作请求头 | 这是 B2 方案的固有取舍：令牌对**已解锁**的前端 JS 可见 |

两者均：`path=/`、`sameSite=lax`、生产环境 `secure`、有效期 30 天。

## 5. 放行清单（不拦截）

后端 `site_gate` 对下列请求**不**要求令牌，否则会破坏正常链路：

| 放行项 | 原因 |
| --- | --- |
| `OPTIONS`（CORS 预检） | 预检带不了自定义头；交给最外层 CORS 处理 |
| `/health`、`/health/ready` | 探活/就绪检查，需对编排器开放 |
| `/auth/oauth/*` | OAuth 是浏览器**顶层跳转** + 第三方**服务端回调**，无法携带 `X-Gate-Token` |

> 前端侧匹配器同样排除内部路径：`/((?!_next|favicon.ico|gate|api/gate|gameweave/).*)`。

**CORS 顺序**：`backend/app/main.py` 把 `CORSMiddleware` 放到**最外层**，并把 `X-Gate-Token` 加入 `allow_headers`。
这样 CORS 预检能正确短路，且门禁的 `401` 响应也会带上 CORS 头（浏览器能干净读到 401，而不是报跨域错误）。

## 6. 安全性与边界

**已具备**
- 密码仅服务端读取，不进客户端包；cookie/请求头是 sha256 哈希令牌，非明文。
- 前后端校验均为**常数时间比较**（前端 `safeEqual`、后端 `hmac.compare_digest`），降低时序爆破。
- httpOnly 的 `pf_gate` 无法被 JS 读取或伪造，守住前端页面门。

**边界（明确取舍）**
- 这是一道「共享访问口令」式的**软门禁**，不是按用户的细粒度鉴权；用户级权限仍由 JWT/OAuth 负责。
- `pf_gate_token` 对已解锁的前端可见 —— 已通过密码的人本就持有等价凭证，可接受。
- **对象存储（MinIO）不在这道门后**：Play 页是浏览器**直连**对象存储加载游戏 bundle 的（独立服务、设计上匿名只读）。如需保护，应在对象存储侧单独配置（见 [安全与可观测性](安全与可观测性.md)）。
- **`/docs` / OpenAPI**：设密码后也会被后端门挡住（属于「后端直连」）；默认无密码时照常开放，对齐 README 宣传的 `:8000/docs`。

**更强的隔离（可选）**：若要后端**端口都不对外暴露**，可加一层反向代理（如 Caddy）作为唯一入口、内网转发后端，整站同源后这道门天然覆盖一切。本仓库未采用，保持双端口架构以最小改动接入门禁。
