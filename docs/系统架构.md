## 技术选型

整体技术栈如下（取舍理由详见 [技术选型](技术选型.md)）：

- **前端**：Next.js 15 + React 19（TypeScript）、TanStack Query、Tailwind CSS v4 + shadcn/ui
- **后端**：Python + FastAPI、SQLAlchemy 2.0 + Alembic、Pydantic v2
- **多智能体**：LangGraph（固定状态图）→ GPT-5.5（OpenAI 兼容接口）
- **异步任务**：Celery + Redis（任务队列 broker）
- **数据库**：PostgreSQL
- **对象存储**：MinIO / S3（boto3，存 bundle + 素材）
- **鉴权**：HttpOnly JWT Cookie + bcrypt、OAuth（Google / GitHub）、Origin-based CSRF 防护
- **测试 / CI**：pytest + GitHub Actions（后端 pytest + 前端 tsc）
- **部署**：Docker Compose（web / api / worker / postgres / redis / minio）、Zeabur

    UI -->|"REST + HttpOnly Cookie"| API
    UI -->|"沙箱 iframe 加载 manifest+bundle"| OSS

**关键边界**

- 前端**不直接读写数据库**，全部走 FastAPI REST 接口（HttpOnly Cookie 鉴权）。
- 前端 Play 页**直接从 OSS 拉远端 bundle**（沙箱 iframe），证明产物来自远端地址。
- 所有 OSS 访问走 `boto3`（S3 SDK），换真 S3/OSS 仅改 endpoint。
- 耗时的生成逻辑放在 **Celery Worker**，API 立即返回 `taskId`；任务详情通过 SSE 实时推送，30 秒查询仅作为断线兜底。

## 4. 多智能体生成流水线（LangGraph）

Create 链路的核心是一张**顶层固定的 LangGraph 状态图**：18 个功能节点 + `done` / `failed`，3 道条件闸门（`safety_intake` / `build_validation` / `gameplay_qa`）与 3 条自愈回环（`repair` / `gameplay_repair` / `replan`）。顶层固定保证安全检查、构建校验、上传发布不被跳过；18 个节点里仅 7 个调用模型，"智能"被约束在节点内部；闸门不过则回环重试，把模型偶发的坏产出在管线内消化。

### 4.1 状态图（节点与回环）

```mermaid
flowchart TB
    START(["开始"]) --> safety{{"◆ safety_intake"}}
    safety -->|"不安全"| failed["failed"]
    safety --> memory["memory_retrieval"]
    memory --> intent["intent_spec ★"]
    intent --> brief["brief_expansion ★"]
    brief --> mech["mechanic_planner ★"]
    mech --> arch["archetype_router"]
    arch --> asset["asset_processing"]
    asset --> design["game_design ★"]
    design --> content["content_plan"]
    content --> balance["balance_plan"]
    balance --> code["code_generation ★"]
    code --> build{{"◆ build_validation"}}
    build -->|"通过"| qa{{"◆ gameplay_qa"}}
    build -->|"代码错 ≤2"| repair["repair_code ★"]
    repair --> build
    build -->|"修不好 ≤1"| replan["replan_game_design ★"]
    qa -->|"玩法差 ≤2"| gprepair["gameplay_repair"]
    gprepair --> code
    qa -->|"改设计 ≤1"| replan
    replan --> balance
    qa -->|"通过"| publish["publish_artifact"]
    publish --> memupdate["memory_update"]
    memupdate --> done(["完成"])
    build -. 耗尽 .-> failed
    qa -. 耗尽 .-> failed
```

**图例与说明**

- `★` = 调用 GPT-5.5 的节点（共 7 个）：`intent_spec` / `brief_expansion` / `mechanic_planner` / `game_design` / `code_generation` / `repair_code` / `replan_game_design`，其余为确定性 Python。
- `◆` = 条件闸门：`safety_intake`（安全拦截）、`build_validation`（静态校验 + V8 冒烟）、`gameplay_qa`（玩法验收）。
- 三条回环各自回到不同步骤：`repair_code` → `build_validation`（改代码，≤2 次）；`gameplay_repair` → `code_generation`（调数值，≤2 次）；`replan_game_design` → `balance_plan`（改设计，≤1 次）。
- 回环上限定义在 `backend/app/agents/state.py`，节点连边在 `backend/app/agents/graph.py`。

### 4.2 状态累积（每个节点追加的内容）

以创意「躲避陨石、射击敌人的太空飞船」为例，看主流程节点依次往共享状态 `GenerationState`（`backend/app/agents/state.py`）追加了什么。下表数值取自确定性兜底路径（`use_real=False`，可精确复现）；开真模型时字段形状一致、内容更丰富。

| # | 节点 | 调模型 | 作用 | 往 state 追加（太空射击示例） |
| --- | --- | --- | --- | --- |
| 1 | `safety_intake` ◆ | 否 | 入口安全检查。检查 prompt 是否为空、过长，是否包含 prompt injection、读取 cookie / 环境变量、窃取密钥等越权意图；不通过就直接进入失败态，不让危险输入流入后续 Agent。 | `normalized_prompt`、`safety_result`{passed:true} |
| 2 | `memory_retrieval` | 否 | 检索用户长期偏好和当前游戏项目记忆。记忆只作为不可信产品上下文，不能覆盖本次输入或安全规则。 | `retrieved_memories`、`memory_context` |
| 3 | `intent_spec` | 是 | 理解用户创意。把自然语言 prompt 转成结构化 GameSpec，确定标题、类型、主题、核心循环、操作方式、胜负条件和标签，让后续节点不再直接面对模糊文本。 | `game_spec`{title:Space Fortress, genre:shooter, theme:space} |
| 4 | `brief_expansion` | 是 | 扩展玩法简报。把一句话创意补成更完整的可玩 brief，明确玩家幻想、目标、核心动词、奖励循环、难度节奏、反馈方式和最小内容量。 | `expanded_brief`{core_verbs:[fly,dodge,shoot], min_content} |
| 5 | `mechanic_planner` | 是 | 规划核心机制。决定游戏具体怎么玩，包括主要操作、次要操作、敌人行为、奖励物、道具、风险模型和玩家技能考验。 | `mechanic_plan`{enemies:[swarm,gunship,boss], powerups×3} |
| 6 | `archetype_router` | 否 | 选择玩法原型。把创意路由到系统支持的类型，例如纵版射击、跑酷、俯视角收集或逻辑解谜，限制生成范围，提升代码生成和 QA 的稳定性。 | `archetype_result`=vertical_shooter（写回 `game_spec.archetype`） |
| 7 | `asset_processing` | 否 | 处理上传素材。把用户上传的图片、视频或文件整理成素材清单，生成封面或素材引用，让素材能被后续设计、代码生成和打包阶段消费。 | `asset_manifest`{cover:渐变, assets:[]} |
| 8 | `game_design` | 是 | 生成具体游戏设计。基于 spec、brief、机制和原型，设计游戏实体、规则、关卡、敌人、Boss、反馈、界面结构和运行时约束。 | `game_design`{900×600, entities, waves, boss:mothership} |
| 9 | `content_plan` | 否 | 安排内容节奏。决定教学如何出现、波次如何推进、奖励和风险如何分布，让游戏不是只有一个空循环，而是有阶段、有变化。 | `content_plan`{tutorial, waves[4], hazard/reward 名} |
| 10 | `balance_plan` | 否 | 生成数值配置。确定游戏时长、目标分、生命值、玩家速度、敌人速度、刷新间隔、最大敌人数等参数，直接影响游戏是否可玩、是否过难。 | `balance_config`{65s · target170 · lives4 · spawn1750ms} |
| 11 | `code_generation` | 是 | 生成可运行代码。根据前面累计的设计和数值产出 `index.html`、`style.css`、`game.js`；2D 模型优先并有模板兜底，3D 则围绕 WebGL / Three.js 产物生成。 | `generated_files`[index.html · style.css · game.js] |
| 12 | `build_validation` ◆ | 否 | 构建与安全校验。检查文件是否齐全、HTML 是否正确引用 JS、是否包含危险 API 或外链、文件体积是否超限，并计算产物 hash；不通过就触发修复。 | `validation_result`{valid, 每文件 sha256/size} |
| 13 | `repair_code` ↻ | 是 | 代码修复回环。只在构建校验失败时触发，根据错误原因局部重写或修复代码，然后回到 `build_validation` 再检查；次数有上限，避免无限修。 | 重写 `game.js`（带报错），`repair_attempts++` |
| 14 | `replan_game_design` ↻ | 是 | 降级重规划。当前设计反复无法实现时，重新生成更简单、更稳定的方案，再回到 `balance_plan` 重跑后半段；2D 场景会启用模板兜底。 | 简化 `game_design`，`use_template_code=true` |
| 15 | `gameplay_qa` ◆ | 否 | 玩法 QA。检查游戏不只是代码没报错，而是真的有循环、输入、目标、得分、失败 / 重开机制，并通过运行时冒烟测试。 | `gameplay_qa_result`{passed, runtime_smoke_ok} |
| 16 | `gameplay_repair` ↻ | 否 | 玩法修复回环。玩法 QA 不通过时，不推翻整个设计，而是调安全数值，例如降低难度、放慢障碍、增加生命或降低目标分，再回到代码生成。 | 放宽 `balance_config`（hazard 变慢 / +命） |
| 17 | `publish_artifact` | 否 | 产物发布。这个节点不调模型，只做确定性工程动作：上传 bundle 到 MinIO / S3，生成 manifest，写入 `Game` 和 `GameVersion`，返回预览地址。 | `game_id`、`version_id`、`manifest_url`、`/play/{id}` |
| 18 | `memory_update` | 条件调用 | 保存原始证据；真实模型启用时由 LLM 建议 claim，程序验证 evidence/scope 并执行状态机。明确冲突 supersede，推断冲突进入后台 candidate，重复证据自动晋升，同时用构建/玩法结果更新已检索 Profile 的效用。 | `memory_items`、`memory_profiles`、`memory_profile_versions` |

> `◆` = 条件闸门；`↻` = 失败时才触发的回环（不新增字段，只重写已有状态）。前 10 个规划/上下文节点把一句话逐层翻译成越来越具体的设计，第 11 个变成代码，12 / 15 把关，13 / 14 / 16 出问题时回头修。

### 4.3 Preview 反馈与增量修改

首次生成和 Preview 后修改使用两条不同路径。首次生成走 `code_generation`；用户反馈不会回到该节点重建整个项目，而是创建独立的 `revision` task，并以用户刚刚预览的版本作为不可变基线。

```mermaid
flowchart TB
    preview["Preview vN"] --> feedback["用户自然语言反馈"]
    feedback --> safety{{"◆ safety_intake"}}
    safety --> memory["memory_retrieval\n检索当前游戏历史反馈"]
    memory --> understand["feedback_understanding ★\n生成自然语言修改简报"]
    understand --> revise["code_revision ★\n读取并修改 vN 现有文件"]
    revise --> validate{{"◆ build_validation"}}
    validate -->|"失败 ≤2"| repair["revision_repair ★"]
    repair --> validate
    validate -->|"通过"| qa{{"◆ gameplay_qa"}}
    qa -->|"失败 ≤2"| repair
    qa -->|"通过"| version["publish_revision\n写入 vN+1"]
    version --> memupdate["memory_update\n保存本轮反馈"]
    memupdate --> preview2["Preview vN+1"]
    preview2 -->|"继续反馈"| feedback
    preview2 -->|"确认"| publish["POST /games/{id}/publish"]
    safety -. "不安全" .-> failed["failed"]
    validate -. "耗尽" .-> failed
    qa -. "耗尽" .-> failed
```

反馈数据采用“两层表示”，避免用固定 JSON 压缩用户想法：

- `feedback_text`：原样保存用户输入，是最终语义依据，不允许被结构化结果覆盖。
- `feedback_brief`：模型生成的自然语言修改简报，描述修改目标、保持不变的内容、可能影响和不确定点。
- 执行节点同时读取 `feedback_text`、`feedback_brief`、现有 `game_spec/game_design` 和 vN 的真实文件；JSON 只承载任务状态，不代替用户表达。

`code_revision` 要求模型只返回确实需要改变的文件。系统按路径把这些文件合并到 vN，其余文件逐字节保留；随后比较 hash 得到 `changed_files`。如果没有产生实际差异，校验失败，不允许用“修改成功”的状态掩盖无效修改。

语义修改必须启用真实模型；离线模式只保留反馈和基线代码，不会伪造修改效果，最终会因 `changed_files` 为空而失败关闭。

版本约束：

- revision task 创建时记录 `base_game_id` 和 `base_version`。
- 写入 vN+1 前再次检查 `game.current_version == base_version`，防止两个并发修改覆盖彼此。
- 每轮修改都创建新的 `GameVersion`，旧版本和旧代码继续保留，可用于比较和回滚。
- 当前阶段只允许修改未正式发布的 Preview；已发布游戏需要先进入编辑/下架流程，避免未经确认的修改直接影响线上版本。

### 4.4 Memory System

当前已实现第一版长期记忆系统。完整设计见 [Memory System 设计](memory_system_design.md)。

记忆系统只作为生成上下文，不改变现有安全边界。优先级固定为：

```text
本次用户输入
> 当前游戏项目记忆
> 用户长期记忆
> 平台默认生成策略
```

设计上新增两个 Agent 节点：

- `memory_retrieval`：在 `safety_intake` 之后执行，按 `user_id` / `game_id` / `category` 检索相关记忆，注入到 `intent_spec` 或 `feedback_understanding`。
- `memory_update`：在发布成功后保存原始证据；一致证据强化、明确冲突取代、推断性冲突进入后台 candidate。candidate 由不同来源的重复证据自动晋升或到期淘汰，不阻塞用户流程。
- `memory_update` 同时将最终 `build_validation` / `gameplay_qa` 结果写成已检索 Profile 的低权重效用反馈。效用用于检索排序与审计，不直接决定事实真值。

生成路径：

```mermaid
flowchart TD
    idea["用户 idea"] --> safety{{"◆ safety_intake"}}
    safety --> retrieval["memory_retrieval\n检索用户偏好/项目约束"]
    retrieval --> intent["intent_spec ★"]
    intent --> design["后续设计与代码生成"]
    design --> preview["Preview"]
    preview --> update["memory_update\n写入候选记忆"]
```

Revision 路径：

```mermaid
flowchart TD
    feedback["用户 feedback_text"] --> safety{{"◆ safety_intake"}}
    safety --> retrieval["memory_retrieval\n检索当前游戏历史反馈"]
    retrieval --> understand["feedback_understanding ★"]
    understand --> revision["code_revision ★"]
    revision --> publish["publish_revision"]
    publish --> update["memory_update"]
```

约束：

- 记忆必须保留原文，模型提取的偏好只能作为辅助索引，不能覆盖 `feedback_text`。
- 记忆文本按“不可信上下文”处理，不能成为系统指令，不能绕过 forbidden API / sandbox / safety 规则。
- 当前使用 PostgreSQL 普通表保存原文和 JSON embedding，BM25 与余弦相似度分别排序后用 RRF 融合；embedding 服务失败时自动退化为词法检索。数据量增大后可迁移 `pgvector`。
- 用户必须能查看、删除、关闭记忆；关闭后生成流程不检索、不写入记忆。
- `memory_items` 是不可替代的证据层，`memory_profiles` 是当前生效状态，`memory_profile_versions` 保存每次状态变化。
- 冲突只在相同用户、相同范围、相同 `profile_key` 内判断；game Profile 可以局部覆盖 user Profile，但不能将其作废。
- 明确的新值可以 supersede 旧值；歧义冲突进入 candidate，旧值继续生效。candidate 达到独立支持次数和置信度阈值后自动晋升，不要求用户确认。
- LLM 只负责提出结构化 claim；`evidence_span`、scope 提升、冲突转换和数据库写入均由程序验证与状态机完成。
- Prompt 优先级为：当前输入 > 当前游戏 Profile > 用户 Profile > RRF 原始证据 > 默认策略。

## 5. Play 加载时序图

```mermaid
sequenceDiagram
    actor U as 用户
    participant FE as Next.js 前端<br/>Home / Play
    participant API as FastAPI 后端
    participant DB as PostgreSQL
    participant OSS as MinIO / S3
    participant IFRAME as sandbox iframe<br/>游戏运行时

    U->>FE: 点击游戏卡片
    FE->>API: GET /games/{id}
    API->>DB: 查询游戏 meta / 当前版本 / 发布状态
    DB-->>API: 返回游戏信息 + current_version
    API-->>FE: 返回 title / author / version / manifest 信息

    FE->>API: POST /games/{id}/play
    API->>DB: 写 play_event / 更新 plays_count
    DB-->>API: 写入成功
    API-->>FE: 返回 ok

    FE->>API: GET /games/{id}/manifest
    API->>DB: 查询 GameVersion.manifest_key
    DB-->>API: 返回 manifest_key
    API->>OSS: 读取 games/{id}/v1/manifest.json
    OSS-->>API: 返回 manifest.json
    API-->>FE: 返回 manifest + entry_url + permissions

    FE->>IFRAME: 创建 <iframe sandbox>
    IFRAME->>OSS: 加载 entry_url / index.html
    OSS-->>IFRAME: 返回 index.html
    IFRAME->>OSS: 加载 game.js / style.css / assets
    OSS-->>IFRAME: 返回游戏 bundle

    IFRAME-->>U: 游戏开始运行
    U->>IFRAME: 操作游戏

    IFRAME->>FE: postMessage(score / game event)
    FE->>API: POST /games/{id}/score
    API->>DB: 保存分数 / 排行榜记录
    DB-->>API: 写入成功
    API-->>FE: 返回排行榜状态

    alt manifest 或 bundle 加载失败
        FE-->>U: 展示错误态 / 重试 / 返回首页
    end
```
