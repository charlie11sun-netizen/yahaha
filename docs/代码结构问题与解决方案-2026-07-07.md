## 1. 前端 `create` 和 `me` 页面职责过重

### 问题

`frontend/app/create/page.tsx` 和 `frontend/app/me/page.tsx` 同时包含页面编排、UI 子组件、状态派生、格式化逻辑和 API 查询 hook。页面文件变大后，新增功能时需要在同一个文件里跨区域修改，影响阅读和回归判断。

### 解决方案

- 保持路由路径和页面入口不变。
- `create` 路由新增 route-local 目录：
  - `frontend/app/create/_components/CreatePanels.tsx`
  - `frontend/app/create/_lib/create-state.ts`
  - `frontend/app/create/_lib/use-create-queries.ts`
- `me` 路由新增 route-local 目录：
  - `frontend/app/me/_components/StudioPanels.tsx`
  - `frontend/app/me/_lib/studio-format.ts`
  - `frontend/app/me/_lib/studio-state.ts`
  - `frontend/app/me/_lib/use-studio-queries.ts`
- 页面入口保留路由编排、URL 参数、主要事件处理和认证跳转；可复用的 UI、格式化和查询状态移到本路由私有目录。

### 后续收益

- 后续调整 Create 面板或 Studio 面板时，不需要继续扩大 `page.tsx`。
- route-local 边界清晰，不会过早抽成全局组件。

## 2. Agent 节点文件过大

### 问题

`backend/app/agents/nodes.py` 集中了 planning、codegen、validation、repair、publish、memory 等多个阶段的节点实现。该文件承担了过多职责，导致单点修改容易影响整个 agent graph，也不利于按阶段理解生成链路。

### 解决方案

- 按职责拆出模块：
  - `backend/app/agents/planning.py`
  - `backend/app/agents/codegen.py`
  - `backend/app/agents/validation_nodes.py`
  - `backend/app/agents/repair.py`
  - `backend/app/agents/publish.py`
  - `backend/app/agents/memory.py`
  - `backend/app/agents/nodes_common.py`
- `backend/app/agents/nodes.py` 保留为兼容层，继续导出原节点函数。
- `graph.py` 的节点名和外部行为保持不变，避免大改 graph wiring。

### 后续收益

- 后续修改某个 agent 阶段时，可以只进入对应模块。
- 节点名和导出兼容，降低回归面。

## 3. Router 混入业务动作

### 问题

`backend/app/api/routers/games.py` 和 `backend/app/api/routers/tasks.py` 原先承担了较多核心业务动作，包括游戏发布、任务创建、重试、取消、修订等逻辑。这样会让 router 同时处理 HTTP、权限、事务和业务规则，后续复用或单测都比较困难。

### 解决方案

- 新增 service 层：
  - `backend/app/services/game_actions.py`
  - `backend/app/services/task_actions.py`
  - `backend/app/services/errors.py`
- 将核心业务动作下沉到 service：
  - 游戏相关动作集中到 `game_actions.py`。
  - 任务创建、重试、取消、修订等动作集中到 `task_actions.py`。
  - service 异常通过统一错误类型向 router 报告。
- Router 保留 HTTP adapter 职责：
  - 解析入参。
  - 获取当前用户和 DB session。
  - 调用 service。
  - 将 service 错误转换为 HTTP response。

### 后续收益

- 业务规则可以在 service 层单测，不必通过 HTTP 才能覆盖。
- router 文件更薄，职责更接近 FastAPI adapter。

## 4. API 契约缺少单一来源

### 问题

主要 response 如果直接返回 dict 或未集中声明模型，前后端字段容易漂移。即使 OpenAPI 能生成，也缺少清晰的 Pydantic response model 作为后端契约来源。

### 解决方案

- 在 `backend/app/schemas.py` 为主要 response 增加 Pydantic model。
- 在 routers 上补充 `response_model`，让 OpenAPI 从后端 schema 生成更准确的接口描述。
- 保留现有响应结构，不为了契约整理改变外部字段语义。

### 后续收益

- OpenAPI 可以进一步作为前端类型生成来源。
- 后端字段调整会更容易被类型和 schema 暴露出来。

## 5. 全局样式范围过大

### 问题

`frontend/app/layout.tsx` 原先全站加载 `globals.css` 和 `homepage.css`。同时，`globals.css` 中包含大量 legacy `pf-*` 页面样式和全局装饰效果，例如 `body::after`。这会带来两个问题：

- 首页样式虽然已有 `.fp-home` 前缀，但仍作为全站 CSS 进入所有页面。
- legacy `pf-*` 规则和全局效果对新 shadcn 页面、`/gate` 等页面也有潜在影响。

### 解决方案

- `homepage.css` 改为只在 `frontend/app/page.tsx` 中导入。
- 新增 `frontend/app/legacy-pf.css`，把 legacy `pf-*` 样式从 `globals.css` 拆出。
- 新增 `frontend/app/app-shell.tsx`：
  - 默认使用 `app-root-layout` / `app-root-main`。
  - 需要旧 `pf-*` 样式的路由加 `pf-legacy-scope`。
  - `/` 和 `/gate` 不加 legacy scope。
- `globals.css` 只保留 Tailwind、design tokens、基础 reset、app shell 和通用 focus 样式。
- `legacy-pf.css` 中普通选择器统一限定在 `.pf-legacy-scope` 下，降低跨页面影响。

### 后续收益

- 首页样式不再由 root layout 全站引入。
- legacy 样式仍可服务旧页面，但影响范围被显式收窄。
- 后续迁移某个页面出 `pf-*` 时，只需要让该路由不依赖 legacy scope。
