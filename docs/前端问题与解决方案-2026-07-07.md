## 1. 首页视频抽帧与动画循环性能风险

### 问题

首页在 `frontend/app/page.tsx` 中会从首页视频抽取最多 120 个 `ImageBitmap` 帧，并通过多个 `requestAnimationFrame` 循环持续运行滚动视频、粒子和卡片 reveal 动画。

风险点：

- 移动端和触控设备上抽帧会增加内存占用和 CPU 压力。
- 粒子动画和滚动绘制原本是常驻 RAF 循环，即使用户没有滚动也会持续调度。
- CSS 已声明 `prefers-reduced-motion`，但 JS 动画逻辑没有跟随用户的 reduced-motion 偏好。

### 解决方案

在 `frontend/app/page.tsx` 中加入运行时资源保护：

- 使用 `matchMedia("(prefers-reduced-motion: reduce)")` 识别减少动态效果偏好。
- 使用 `matchMedia("(max-width: 768px), (hover: none), (pointer: coarse)")` 识别移动端、触控设备等资源敏感环境。
- reduced-motion 或资源敏感环境下跳过 `ImageBitmap` 抽帧，并停止粒子动画。
- 桌面端保留滚动视频效果，但将抽帧上限从 120 降到 72，并从 24fps 降到 18fps。
- 将滚动视频和卡片 reveal 从永久 RAF 循环改为滚动、resize、视频加载等事件触发的按需 RAF。
- 页面隐藏时暂停粒子动画；组件卸载时取消 RAF 并释放 `ImageBitmap`。

### 结果

桌面端仍保留首页核心视觉效果；移动端和 reduced-motion 用户会走更轻量的路径，降低 CPU 和内存压力。

## 2. Explore Featured 卡片嵌套交互语义不正确

### 问题

`frontend/app/explore/page.tsx` 的 `ShowcaseCard` 中，外层是一个 `button`，内部又放了带 `onClick` 的 `span` 作为 Play 操作。

风险点：

- 可点击元素嵌套在另一个按钮语义内，DOM 交互结构不干净。
- 键盘、屏幕阅读器和浏览器默认交互行为可能不一致。
- 需要依赖 `stopPropagation` 才能区分打开详情和播放两个动作。

### 解决方案

重构 `ShowcaseCard` 的媒体区域：

- 外层从 `button` 改为普通 `div` 容器。
- 图片区域新增一个覆盖式 `button`，用于打开详情，并添加 `aria-label`。
- Play 操作改为独立 `button`。
- 装饰性 overlay、badge、标题文案使用 `pointer-events-none`，避免影响真实按钮命中。

### 结果

视觉基本不变，但打开详情和播放两个动作现在是两个独立、合法、可访问的交互元素。

## 3. `globals.css` 中任务表格样式重复覆盖

### 问题

`frontend/app/globals.css` 中 `.pf-studio-task-table`、`.pf-studio-task-head`、`.pf-studio-task-row` 有两套定义。后面的定义覆盖前面的列宽、padding 和 overflow 行为。

风险点：

- 维护者需要知道后面还有一套覆盖规则，容易改错。
- 样式结果依赖文件顺序，而不是单一清晰定义。
- 后面的 `overflow: hidden` 会覆盖前面的 `overflow-x: auto`，窄屏下任务表格存在被裁切风险。

### 解决方案

在 `frontend/app/globals.css` 中合并任务表格样式：

- 将最终使用的列宽、`min-width: 1014px`、表头背景、padding、边框和圆角合并到第一处定义。
- 删除后面重复的覆盖块。
- 保留 `overflow-x: auto`，让窄屏可以横向滚动查看完整任务表格。

### 结果

任务表格样式只保留一套主要定义，减少 cascade 顺序依赖，同时保留最终视觉效果并改善窄屏可用性。
